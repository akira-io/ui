# Akira UI: open-source fork of nosferry-ui with brand theming

Date: 2026-07-31
Status: approved design, not yet implemented

## Goal

Publish the shared component library as a public, open-source package under a brand-neutral name, with the
Akira purple as the default palette and a documented way for any project or company to swap in its own brand
color. NosFerry becomes one consumer among others rather than the identity of the library.

## Non-goals

- Deprecating, changing, or republishing `@akira-io/nosferry-ui`. It stays exactly as it is on GitHub Packages.
- A runtime theme provider, multi-tenant theming, or colors loaded from a database. Theming is build-time CSS.
- Hosting the written documentation on the preview site. `docs/` stays in the repo; the site links to it.
- Any change to component APIs. The only component-level change is the tour popover class name.

## Color values

The Akira palette is a full 50–950 ramp built on the lightness and chroma curve of Tailwind v4's `violet`,
with the hue fixed at 288 and the chroma scaled by 0.848. That places step 500 exactly on the Akira banner
purple, `#7c5cf0`. Every step was converted from OKLCH to sRGB and checked to be in gamut; contrast ratios below
are computed, not estimated.

### The 600/400 rule

`--primary` is step 600 in light mode over a white foreground, and step 400 in dark mode over the near-black
ink `oklch(0.161 0.027 294)`. This is the same pairing Tailwind and shadcn use, and it is what every brand
preset must follow.

| Role | Value | Hex | Contrast |
| --- | --- | --- | --- |
| `--primary` (light) | `var(--color-akira-600)` | `#6c3ce7` | 5.84:1 |
| `--primary-foreground` (light) | `oklch(0.985 0 0)` | `#fafafa` | N/A |
| `--primary` (dark) | `var(--color-akira-400)` | `#9687f3` | 6.54:1 |
| `--primary-foreground` (dark) | `oklch(0.161 0.027 294)` | `#0e0b18` | N/A |

The banner purple itself, step 500, is deliberately not `--primary`: it reaches only 4.32:1 against white and
fails WCAG AA for normal text. It stays available as `bg-akira-500` for surfaces that carry no text.

### NosFerry preset

The current NosFerry red, `oklch(0.577 0.245 27.325)`, is byte-for-byte Tailwind's `red-600`, so the preset
already satisfied the rule in light mode. It did not in dark, where it repeats `red-600`. The preset moves to
`red-400`, `oklch(0.704 0.191 22.216)` (`#ff6467`), which reaches 6.72:1 against ink. Apps see this change at
migration time, alongside the ring and specifier changes.

## Theme architecture

`theme.css` remains the single source of truth. The `@theme` block gains the eleven `--color-akira-*` steps,
which makes `bg-akira-500`, `text-akira-700` and `border-akira-200` available in every consuming app. The
semantic tokens then reference the ramp rather than repeating literals, so the origin of the brand color is
visible in the file:

```css
@theme {
    --color-akira-50: oklch(0.951 0.014 288);
    /* … through … */
    --color-akira-950: oklch(0.265 0.12 288);
}

:root {
    --primary: var(--color-akira-600);
    --primary-foreground: oklch(0.985 0 0);
    --ring: var(--primary);
    --sidebar-primary: var(--primary);
    --sidebar-primary-foreground: var(--primary-foreground);
}

.dark {
    --primary: var(--color-akira-400);
    --primary-foreground: oklch(0.161 0.027 294);
}
```

A preset overrides `--primary` and `--primary-foreground` with its own literals; the `--color-akira-*` ramp
stays available regardless of which brand is active, since it is a palette, not a semantic token.

`--ring` changes behavior: today it is a neutral near-black in light and light gray in dark. From v1.0.0 the
focus ring carries the brand color everywhere.

### Preset contract

A brand preset is a CSS file that declares exactly four values and nothing else (the 600 and 400 steps of the
brand's own ramp, with white and ink on top) scoped to a `data-brand` attribute:

```css
/* themes/nosferry.css */
[data-brand='nosferry'] {
    --primary: oklch(0.577 0.245 27.325); /* red-600 */
    --primary-foreground: oklch(0.985 0 0);
}

[data-brand='nosferry'].dark {
    --primary: oklch(0.704 0.191 22.216); /* red-400 */
    --primary-foreground: oklch(0.161 0.027 294);
}
```

The consuming app sets the attribute once, on the same element that carries the dark class:

```html
<html data-brand="nosferry" class="dark">
```

The base stylesheet keeps Akira on `:root`, so an app that sets no attribute is Akira with nothing to import.
Scoping presets to an attribute instead of `:root` is what lets the preview site switch brands live without
keeping its own copy of the colors: the switcher toggles the attribute and the shipped CSS does the rest.

Because `--ring` and the sidebar primary tokens reference `var(--primary)`, they follow automatically. Neutrals,
surfaces, borders and `--destructive` are identical across every brand, which is what keeps contrast predictable
without re-checking each preset by hand.

A brand that has no ramp of its own can take the pair straight from Tailwind's palette, as NosFerry does. A
brand with a custom hue builds its ramp the way the Akira one was built: pick the Tailwind ramp with the nearest
hue, keep its lightness and chroma curve, shift the hue, and scale the chroma so step 500 lands on the brand
color.

### Consumption

Akira default, nothing to import beyond the base:

```css
@import '@akira-io/ui/theme.css';
```

NosFerry, or any other brand, imports the preset after the base and sets the attribute on `<html>`. Import order
is load-bearing:

```css
@import '@akira-io/ui/theme.css';
@import '@akira-io/ui/themes/nosferry.css';
```

An external company that does not want its palette in the package writes the same four declarations directly in
its own stylesheet, under its own `data-brand` value. Documented, not shipped.

## Preview site

A separate public repo, `kidiatoliny/ui`, is the landing page and component gallery (the same role the shadcn
site plays for shadcn). It follows `payable-docs`: Astro, `@astrojs/react`, Tailwind v4, deployed on Vercel.

### Structure

A landing page with the pitch, the install command and a few highlighted previews, then a gallery covering all
75 entries: 55 components under `ui`, 8 blocks, 12 shells. Components and blocks preview inside a bordered
card; shells are full-screen layouts and get their own route each, previewed in an iframe so their sidebar and
header do not fight the site chrome.

### Demos are real files

Every variation is a `.tsx` file under the site's demo directory. The site imports it to render the preview and
reads the same file as raw text for the code block, so the snippet cannot drift from what runs. A demo that
fails to compile fails the site build.

### Theme switcher

A control in the header toggles `data-brand` and the `dark` class on `<html>`. Because presets are scoped to
the attribute and shipped by the package, switching between Akira and NosFerry recolors every preview on the
page using exactly the CSS an app would load. The switcher is the product demo, not a site-only feature.

### The site as a release gate

Before the first npm publish, the site consumes the package from a local build rather than the registry. Then
the whole gallery is reviewed: 75 entries rendered in four combinations of brand and color scheme is a far
wider surface than any unit test covers, and it catches contrast, spacing and dark-mode problems while they are
still cheap to fix. Only after that review does 1.0.0 go to npm, at which point the site switches to the
published version and becomes the first public consumer.

## Testing

Three vitest suites, none of which exists today:

1. **Preset contract.** Parse every file in `themes/`. Assert each declares `--primary` and
   `--primary-foreground` under both `[data-brand='<name>']` and `[data-brand='<name>'].dark`, that the brand
   name matches the filename, and that no other custom property is declared. This is what keeps a preset from
   quietly redefining neutrals and drifting from the other brands.
2. **Contrast.** Convert the `--primary` / `--primary-foreground` pair of the base stylesheet and of every
   preset from OKLCH to sRGB, compute the WCAG ratio, and fail below 4.5:1. Covers light and dark separately.
3. **Ramp integrity.** Assert the eleven `--color-akira-*` steps are present, that lightness decreases
   monotonically from 50 to 950, and that every step converts to an in-gamut sRGB color. A step that clips
   silently renders as a different color in the browser than the token claims.

All three read the CSS from disk, so a new preset added later is covered without touching the tests. The OKLCH
to sRGB conversion is shared by suites 2 and 3 and lives in a test helper, not in the published bundle.

## Rollout

1. Create the public repo, copy the tree without history, apply every change above, one initial commit.
2. Create `kidiatoliny/ui` and build the gallery against the local package build.
3. Review all 75 entries in Akira and NosFerry, light and dark. Fix what the review finds in the package, not
   in the site.
4. Manual `npm publish` of 1.0.0, then bind trusted publishing on npmjs.com.
5. Tag `v1.0.0` so git-cliff generates the changelog and the GitHub release.
6. Point the site at the published package and deploy it.
7. Migrate NosFerry apps one at a time: swap the specifier, add the `themes/nosferry.css` import, set
   `data-brand="nosferry"` on `<html>`, verify the focus ring and the tour popover.
8. New apps start on `@akira-io/ui` with no preset and no attribute.

## Risks

- The focus ring changing from neutral to brand is a visible change in every NosFerry app at migration time.
  It is intended, and it lands per app rather than all at once.
- The preset contract is enforced by a test, not by the type system. A consumer that writes its palette inline
  in its own stylesheet is outside that guarantee.
- Trusted publishing requires the manual first publish and the npmjs.com binding to be done before the first
  tag, or the release workflow fails on the publish step.
- Forgetting `data-brand` on `<html>` during a NosFerry migration is silent: the app builds, renders and simply
  comes out purple. The migration section of the docs leads with the attribute for that reason.
- The gallery is 75 entries with several demos each. It is the largest single piece of work in this plan, and
  it grows with the library: a component added later without a demo leaves a hole nothing detects. Adding the
  demo alongside the component becomes part of the contributing guide.
